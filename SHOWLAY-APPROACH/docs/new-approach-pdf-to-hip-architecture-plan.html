Final Version

1. Executive Summary

The goal is to build a proper, extensible backend that can convert healthcare assessment PDF templates of different layouts into a deterministic structure that can be reviewed and exported into HIP Excel workbooks.

Final architecture in one line:
Section-aware PDF extraction → canonical JSON → deterministic normalization → profile-based Excel export.

We are not simply patching the current code. The existing SHOWLAY implementation has useful foundations, but the extraction strategy must be redesigned because complex forms such as MNLOC need document-level and section-level context.

2. Problem We Are Solving

Healthcare programs use PDF assessment forms that must be converted into HIP Assessment Configuration Workbooks. The current developer tool works reasonably for some simple or medium forms, but fails to generalize to complex layouts like MNLOC.

Why the current approach struggles

IssueWhy it mattersRequired design response
Page-by-page extractionComplex forms have section-level context, shared legends, skip logic, and item codes spanning pages.Process by logical section, not isolated pages.
Large form-specific postprocessorMany cleanup rules are overfitted to known samples and may break on new forms.Replace with generic deterministic normalization.
Widget metadata confusionAcroForm field names may be cryptic, wrong, or non-semantic.Use visible rendered text and spatial layout as source of truth.
Golden workbook leakageUsing human-filled workbook during extraction inflates evaluation results.Use golden files only in offline evaluation.
Workbook-specific differencesDifferent templates use different spellings and conventions.Use template profiles during export, not inside extraction.
Important: The system is not extracting user-entered values from filled forms. The samples are blank templates. The task is to extract the form structure: questions, instructions, choices, tables, signatures, validations, and branching rules.

3. Scope & Output Columns

The backend should extract a stable canonical JSON that supports the eight workbook columns currently in scope. Other HIP workbook columns remain manual or business-owned.

In-scope target workbook columns

#ColumnHow it is populated
1SectionDerived from visible form headers and logical grouping. Dense in JSON; sparse only during Excel export if profile requires.
2SequenceGenerated internally as dense 1-based reading order. Export can write or suppress it based on profile.
3Question RuleProfile-controlled. Default blank unless the PDF clearly defines current-row visibility/applicability.
4Question TypeSemantic classification using canonical vocabulary.
5Question TextVisible PDF text, including item codes such as B0200 or GG0170Q5.
6Branching LogicOutgoing skip/show logic. Store both resolved Q-reference and verbatim PDF source.
7Answer TextAll answer options for choice fields, separated using line breaks.
8Answer ValidationPDF-explicit constraints plus mandatory HIP defaults by question type.

Out of scope for v1

Business-owned columns

Auto Populated, Pre Populate, Required, Alert, History, Speech to Text, Submission History, Concept Code, Token ID, Auto Populate with/Field/Rule.

Advanced extraction

Bilingual extraction, Answer Score Value, score calculation, natural-language row correction, and business-only configuration decisions.

4. Design Principles

Canonical JSON first

The extraction engine produces one stable JSON format. Excel is a derived output.

Template profile at export

Workbook-specific spellings and conventions are handled by profiles, not by the agent.

Visible layout is truth

Rendered text and spatial layout are primary. Widgets are supporting evidence only.

Section-aware processing

Complex PDFs like MNLOC are processed by logical sections, not isolated pages.

No golden leakage

Human-filled workbooks are used only for offline evaluation, never during extraction.

Generic extraction

No form-specific code, regexes, title checks, or cleanup rules inside the extraction pipeline.

6. Pipeline Stages

Stage 0 — Template Profile Loader

Loads the workbook profile by explicit selection, auto-detection from template headers, or generic fallback. The profile is used only at export time.

Stage 1 — PDF Ingestion

InputPDF file
ToolsPyMuPDF, page rasterization, Bedrock vision models. Textract remains a future optional layer.
OutputDocStructure with page images, text blocks, widgets, tables, layout blocks, bboxes
RuleVisible rendered text + spatial layout are primary. Widgets support location/type hints only.

Stage 2 — Document Profiler

One LLM call to identify form title, version, page count, sections, shared legends, and extraction strategy.

{
  "form_title": "Medical Necessity and Level of Care Assessment",
  "form_version": "V.21 Effective 09/01/2025",
  "complexity": "complex",
  "sections": [
    {"name": "Section A. Identification Information", "pages": [1, 2]},
    {"name": "Section B. Hearing, Speech, and Vision", "pages": [3]}
  ],
  "extraction_strategy": "section_by_section"
}

Stage 3 — Section Extractor

The main LLM extraction stage. It receives section pages, text blocks, widgets, tables, shared legends, and all-section context.

Extract only meaningful form artifacts. Exclude page numbers, repeated headers, repeated footers, watermarks, decorative separators, and repeated page chrome unless they define required display content.

Stage 4 — Global Normalizer

Deterministic Python functions. No form-specific knowledge.

FunctionPurpose
concatenate_sectionsMerge section outputs in document order.
assign_global_sequenceCreate dense 1-based sequence values.
build_external_id_indexMap item codes such as B0100 to sequence numbers.
resolve_item_code_branchesConvert item-code branching to Q-reference form where possible.
apply_validation_defaultsApply mandatory HIP defaults by question type.
validate_branching_refsFlag unresolved references; allow forward references.
score_confidenceGenerate review risk and confidence scores.

Stage 5 — Review Manifest Builder

Wraps canonical JSON in a SHOWLAY-compatible manifest so the existing UI can still render rows, pages, bboxes, and editable fields.

Stage 6 — Excel Export

Applies the active template profile and writes the workbook. Excel is derived from canonical JSON.

7. Agents Needed

Keep the agent design practical. Do not create one agent per column. Use a small number of intelligent agents and deterministic services.

Agent / ServiceTypeResponsibility
Document Profiler AgentLLMDetect title, version, sections, complexity, shared legends, and extraction strategy.
Section Extraction AgentLLMExtract rows from each section: question type, text, answers, branching, external IDs, source evidence.
Extraction QA / Confidence ServiceMostly deterministic, optional LLM for reviewDetect missing values, invalid types, unresolved references, low-confidence rows.
PDF Ingestion ServiceDeterministicText, widgets, images, layout blocks, bboxes, optional Textract output.
Normalizer ServiceDeterministicSequence, defaults, references, validation, canonical JSON cleanup.
Profile Export ServiceDeterministicMap canonical JSON to target Excel workbook.
Implementation recommendation: Start with two LLM agents: Document Profiler and Section Extractor. Everything else should be deterministic wherever possible.

11. AWS Services

The recommended design is AWS-first because the team already has access to Amazon Bedrock. Alternatives can be benchmarked later if needed.

Amazon Bedrock

Used for the LLM agents: document profiling and section extraction. Model IDs should be configurable and benchmark-driven.

Amazon Textract

Optional document intelligence layer for scanned PDFs, table-heavy pages, checkboxes/selection elements, signatures, and cases where PyMuPDF layout extraction is unreliable.

Textract is not the semantic extractor. It provides OCR/layout/table/form evidence. The LLM/agent still performs HIP question type classification, grouping, option interpretation, and branching interpretation.
Current access constraint: Textract access is not available for the POC right now. Keep it in the architecture as a future feature-flagged document-intelligence layer, but do not implement Textract calls or make v1 acceptance depend on Textract output.

Add Textract-augmented variants only after access is granted.

13. Implementation Plan

Phase 1 — Foundation

Set up backend structure, preserve existing UI endpoints, port PyMuPDF probe/rasterization, add schemas, add profile loader, create manifest contract test.

Acceptance: Existing UI loads, PDF can be uploaded, page images render, fixed manifest works in workbench.

Phase 2 — Simple Form Path

Implement document profiler and single-call section extractor for simple/small forms. Add normalizer, manifest builder, profile-based export.

Acceptance: H1700-3 and CHOICES meet target accuracy, full upload-review-edit-download flow works.

Phase 3 — Section-Aware Complex Path

Add section-by-section extraction, shared legend carry-forward, external ID index, item-code branch resolution, MNLOC profile.

Acceptance: MNLOC processes all 34 pages without crash, all sections navigable, item-code branching preserved.

Phase 4 — Evaluation & Benchmarking

Benchmark the configured model cycle: Nova 2 Lite, Nova Pro escalation, Qwen3-VL, Mistral Large 3, and Kimi K2.5. Add Textract combinations only after access is granted. Evaluate on sample forms plus at least one novel form outside the sample set.

Acceptance: Accuracy/cost dashboard and final production model recommendation.

14. Evaluation Strategy

Golden workbooks are used only for offline evaluation. They must never be read during extraction.

Per-dimension metrics

MetricMeaning
Row recallDid the system find expected questions, display rows, and tables?
Row precisionAre extracted rows real form artifacts?
Question Text accuracyFuzzy match against expected text.
Question Type accuracyExact match after canonical normalization.
Answer Text completenessExpected options recovered for choice rows.
Branching Logic correctnessSkip/show logic captured correctly.
Answer Validation correctnessHIP defaults and explicit constraints applied.
Section assignment accuracyRows assigned to correct section.
Sequence/order correctnessRows in correct relative order.
Question Rule appropriatenessOnly where PDF clearly implies current-row rule.
A single overall score can hide failures. For example, question text can be correct while branching logic is poor. Report metrics separately.

16. Developer Checklist

Do

  • Produce canonical JSON as the primary extraction output.
  • Keep section names dense in JSON.
  • Apply section sparsification only during export if profile requires it.
  • Use visible text and layout as primary truth.
  • Use widgets as supporting evidence only.
  • Allow forward branching references.
  • Use golden workbooks only in offline evaluation.
  • Keep existing UI manifest contract backward-compatible.
  • Keep model IDs configurable.
  • Benchmark model choices before production selection.

Do not

  • Do not hardcode CHOICES, MNLOC, H1700-3, or other form-specific strings in extraction code.
  • Do not use AcroForm field names as question text without visible-label validation.
  • Do not use the golden workbook during extraction.
  • Do not recreate the 38-stage postprocessor.
  • Do not ask the LLM to generate Excel directly.
  • Do not treat page numbers, repeated headers, or footers as rows unless they are meaningful instructions.
  • Do not remove fields from the existing manifest contract.
Final acceptance statement: This design is acceptable for implementation planning after the remaining wording cleanup: replace any remaining “7 columns” with “8 columns, with Question Rule profile-controlled/default blank,” and keep model references configurable/benchmark-driven.
